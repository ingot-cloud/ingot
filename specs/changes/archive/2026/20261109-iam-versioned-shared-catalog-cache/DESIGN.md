# 详细设计

## 已批准实施顺序

先将两条目录读改为单条实时 SQL。菜单 SQL 绑定已经通过实时应用准入的 ID 与当前域；在同一条语句读取菜单和绑定，仍由菜单装配器执行准入。操作目录以应用为左连接根，空目录仍返回应用，平台保留停用项和空资源，租户只返回启用且有启用操作的资源；鉴权和租户开通仍先执行。首期 Redis 短缓存由直查替换，无数据库迁移、HTTP 契约变化或新配置。

以下七天版本方案作为隔离实验候选。只有相同请求率下有明确收益，并获得目标环境热度与目录规模证据后，才进一步决定生产接入。隔离实验的版本字段、模拟写入和 Redis 键不进入生产。

## 长缓存候选的数据库版本

在 `iam_application` 增加内部列 `catalog_revision CHAR(36) NULL`，保存不复用的 UUID。保留 `version` 的公共乐观锁职责。新应用由创建事务生成版本，正式初始化为预制应用赋予新版本，已有库增量回填。读取到 NULL 时查库并跳过缓存，避免未初始化的应用共享固定版本。

每个应用使用一个目录版本，供操作目录与菜单结构共用。应用、资源、操作、菜单及菜单操作绑定的写入在原事务内推进版本，整包创建只产生一个最终版本。变更子目录前按应用、子记录顺序加锁，并核对现有清理、菜单及资源写路径的锁顺序。变更失败或回滚保留旧目录与版本。删除和 `purge` 以应用行消失表示该目录不存在。应用开通、人群、成员及分配变化由实时读路径处理。

版本令牌由主库当前读获得。Redis 只存按版本标识的数据。发布新版本后，后续请求自然改用新 key，原版本由 TTL 回收。以下是候选键结构，本阶段不新增配置。

```text
in:iam:catalog:v2:<appId>:<catalogRevision>:actions:PLATFORM
in:iam:catalog:v2:<appId>:<catalogRevision>:actions:TENANT
in:iam:catalog:v2:<appId>:<catalogRevision>:menu-structure
```

三种载荷固定七天过期，命中不续期。首期旧 key 独立到期。数据库查询、Redis 读写和缓存编解码按现有分层放置，复用单层缓存的故障回源和指标口径。

## 操作目录读取

两个现有入口先执行各自的鉴权与开通校验，应用查询一并取回名称、编码与目录版本。命中直接使用对应版本的资源操作树。冷读或回源使用一条快照查询，从应用左关联资源和操作，同一 SELECT 返回版本、应用头与载荷。平台保留空资源和停用条目；租户视图保留有启用操作的启用资源。按原资源 ID 与操作 ID 顺序组装，合法空树可缓存。

快照版本与入口版本不同时，用快照所见的当前版本重新校验入口条件，避免用已删除应用的旧头组装响应。回填始终使用快照自身的版本。写入事务内的查询直接读库并跳过缓存回填。Redis 不可用时仍从同一快照查询读取。数据库查询失败沿用入口错误处理。

## Bootstrap 菜单读取

保留现有可访问应用和权限求值。使用已经得出的应用 ID 列表，一条批量查询按可信域与应用启用状态限制范围，同时返回应用目录版本、启用菜单 ID、菜单类型、`OPEN/ACTION`、`ANY/ALL` 与关联操作编码。左连接保留开放或未绑定的菜单、无菜单的应用以及关联到停用操作的要求。没有可访问应用时直接返回空导航。该查询承担实时准入与版本检查。

按应用缓存共享结构，包括菜单 ID、父级、名称、路径、视图、路由名、图标、排序、隐藏标识、页面缓存标识和路由参数。服务将实时准入投影叠加到同版本结构后，复用现有组装规则过滤页面并补齐父目录。按应用批量取缓存，仅对未命中的应用一次查询结构及对应版本。缓存内容按应用共享，调用时由当前可访问应用和授权结果控制输出。

冷读的结构版本与准入查询观察到的版本不同时，针对冲突应用用一次完整实时查询重新取得结构与准入投影，在同一语句的结果内组装。该次回退不向 Redis 写入冲突条目。只组合同一版本的结构和准入规则。Redis 错误或载荷损坏等同未命中。结构合法为空也使用明确的版本与空载荷，避免反复查询。

## 查询预算

基准为首期隔离实测及原 Mapper 调用。以下为同夹具的预算；实测见 [验证](./VALIDATION.md)。

| 路径 | 首期 | 合并直查目标 | 版本缓存热读目标 |
|---|---|---|---|
| `bootstrap` 菜单分支，有绑定 | 4 条 SELECT | 1 条 | 1 条 |
| 16 应用普通成员完整 `bootstrap` | 20 条 SELECT | 17 条 | 17 条 |
| 平台 / 普通租户成员 `action-catalog` 完整入口 | 冷读 9 / 18 条，热读 7 / 16 条 | 7 / 16 条 | 7 / 16 条 |

没有可访问应用时跳过菜单 SQL。缓存冷读另有回源和版本校验成本，按实验结果单独记录。并发目录变更、部分命中与 Redis 故障在生产缓存确定接入后使用目标数据另验。

## 评审对照

单条 SQL 可以直接取得菜单展示字段和准入规则，避免跨版本组装。操作目录可以用应用作为左连接根，同时取得应用存在性、目录头、资源与操作；租户开通与鉴权仍走原入口。按首期语句数推算，有绑定的菜单分支从 4 条降至 1 条，平台和租户操作目录整条接口分别预计 7、16 条 SELECT。这两个预算与七天缓存热读相同。

在隔离 MySQL 8.4 和 Redis 8.2.0 中使用现有目录表结构和合成数据，每组预热 30 次，交错采样 200 次。缓存方案测量窄 SQL 加 Redis 热读与 JSON 解码，菜单按应用批量取缓存。表中为读取和整理结果的 P95，HTTP、鉴权和目录写入成本需另测。

| 场景 | 单条 SQL | 窄 SQL + Redis 热读 |
|---|---:|---:|
| 8 个菜单、16 条绑定 | 0.99 ms | 1.27 ms |
| 16 个应用共 128 个菜单、256 条绑定 | 3.44 ms | 3.40 ms |
| 256 个菜单、512 条绑定 | 4.11 ms | 3.76 ms |
| 32 个操作 | 0.89 ms | 1.39 ms |
| 512 个操作 | 3.26 ms | 2.21 ms |

建议先把单条 SQL 作为端到端对照，验证目录和菜单响应等价以及提交后读取。代表性大目录或并发测试中，若版本化 Redis 能稳定改善接口 P95/P99 或降低数据库读取负载，再决定接入的入口。届时七天方案继续使用同事务目录版本和显式 Redis 调用。具体选择进入详细设计评审。

调用频次与目录大小一起决定缓存收益。用目标环境可获得的访问日志或指标按路由统计平时和高峰 QPS，按应用观察目录请求的集中程度、同版本重复读取和目录写入频率。相同 QPS 下对比单条 SQL 与版本化 Redis 的接口延迟、错误率、数据库语句耗时总量、扫描及返回行数、数据库 CPU 与连接池等待，以及 Redis 命中率和回源。缺少目标环境流量数据时，分别报告合成稳态与突发并发结果。

两种读路径都保留实时检查，Redis 热读即使 SELECT 数相同，也可能省去重复的目录关联和展示字段传输。如果高频请求集中读取相同版本，接口延迟接近且数据库负载稳定下降，仍算缓存收益。低命中或写入频繁的场景分别报告，确认版本切换后的冷读与 Redis 故障回源能承受代表性流量。

## 长缓存候选的初始化、发布与回退

- 更新权威目录 DDL、正式种子及生成的初始化文件。已有库采用独立、可重跑的增量 DDL 和版本回填，保留全部业务数据。
- 先应用增量 DDL，再在同次部署中替换目录写节点和读节点，恢复目录写入前核对所有写入都推进版本。数据库脚本直接变更目录时，在同一事务内为受影响的应用换版本。
- 回退时保留新增列并切回前一版代码，七天缓存独立到期。重新切入新版前给应用目录换新 UUID，覆盖回退期间的目录写入。数据库恢复或重新初始化也赋予新版本。
