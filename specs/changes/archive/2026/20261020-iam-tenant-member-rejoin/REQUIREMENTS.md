# Requirements

## 用户场景

1. 租户管理员把成员移出后，用「添加成员」再次提交同一手机号。系统识别已移出资格，复用原成员 ID 重新加入，不报「成员资格已存在」。
2. 管理员在成员列表筛选已移出，对一行执行「重新加入」，可修改姓名、联系方式和部门后提交。
3. 重新加入后该人是新入职状态：任职以本次提交为准，旧角色授权、用户组、部门负责人、人群、策略选择器和委派关系不再生效。

## 业务规则

1. 权限仍为 `iam-tenant:member:create`，不新增操作码。
2. 复用 `iam_tenant_member` 原行：`REMOVED` → `ACTIVE`，成员 ID 不变。
3. 用本次提交覆盖 `display_name`、`phone`、`email`；`avatar` 置空。不修改全局账号。
4. 部门按本次提交整体替换，允许空。
5. 同一事务清理该成员的：
   - 有效角色分配（改为 `REVOKED` 并递增分配 version）
   - 其作为管理员的委派（撤销并撤销派生授权）
   - 委派接收成员行、用户组成员行、部门负责人行、人群成员行、策略选择器成员行（硬删，并递增所属用户组、部门、委派、人群 version）
6. 账号停用仍报「该手机号对应的账号已停用」。
7. 成员为 `ACTIVE` 或 `SUSPENDED` 仍报「成员资格已存在」。
8. 行入口携带 `expectedVersion`；版本冲突拒绝；当前不是 `REMOVED` 拒绝。
9. 响应 `TenantMemberCreated` 增加 `rejoined`。重新加入时 `accountCreated=false`、`rejoined=true`、不返回密码。
10. `joinedAt` 仍取 `created_at`，不加新列。

## 边界与非目标

- 不恢复旧授权；不提供「是否保留原角色」选项。
- 不处理邀请、短信或批量导入重新加入。
- 策略选择器无独立 version，只删除成员引用。
- 平台 `POST /v1/platform/members` 不变。

## 验收标准

- [x] 已移出成员用同一手机号添加成功，`rejoined=true`，成员 ID 不变
- [x] 在职或暂停成员添加仍报「成员资格已存在」
- [x] `POST /{id}/rejoin` 成功后资格为 `ACTIVE`，资料和部门为本次提交
- [x] 旧角色分配、用户组、负责人、人群、选择器、委派管理员/接收者关系已清除
- [x] 版本冲突返回修订冲突；账号停用返回约定文案
- [x] 授权热缓存失效，旧授权不再用于求值
