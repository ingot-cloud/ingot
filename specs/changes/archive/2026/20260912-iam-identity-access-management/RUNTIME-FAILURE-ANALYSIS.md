# 2026-11-10 本机验收错误分析

## 已确认缺陷：成员 JSON 导出和工作簿导入并发登记返回 500

上一轮隔离验收中，同一租户的两笔 `POST /v1/tenant/members/export` 几乎同时到达同一 IAM 节点。一笔返回 200；另一笔返回 500 `S0500`。失败调用栈为 `MemberExportService.create` → `MemberExportRepository.expireDue` → MySQL `DeadlockLoserDataAccessException`。这是数据库事务被回滚，失败请求未登记任务，也没有提交对应审计或派发异步快照。已通过的正常导出、跨节点取件和权限重验结论仍适用。

本轮从正式 SQL 初始化空库，用真实 Gateway、Auth、两个 IAM 实例和同一合成租户。每个入口同时发 8 笔请求，均分到两个节点。`POST /v1/tenant/members/export` 返回 2 个 200、6 个 500；`POST /v1/tenant/members/workbook/import` 返回 1 个 200、7 个 500。所有 13 个 500 都在 IAM 日志中对应 MySQL 死锁，两个节点均出现。成功登记的任务从另一节点读取均为 `SUCCEEDED`；工作簿任务的终态只表示处理结束，不表示每行导入成功。这组数字是并发复验结果，不是线上故障率。

`create` 在同一事务内先执行租户范围的过期清理，再校验组织版本、插入 `PENDING` 任务和写审计。清理按 `tenant_id`、`status IN (...)`、`expires_at <= now` 扫描 `idx_iam_member_export_tenant_status`，即使没有任何过期行，也可能锁住索引区间。快照工作线程则按任务主键更新状态，状态也是该二级索引的一部分。MySQL 8.4 在默认 `REPEATABLE READ` 下的范围更新锁与插入意向锁规则见 [InnoDB 锁说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html)。

使用仓库 `databases/iam/004_policy_audit_migration.sql` 原表结构、MySQL 8.4.13 和合成数据，独立复验：

| 场景 | 可核查结果 |
|---|---|
| 空任务表，两事务各清理 0 行，再并发插入 | 一笔提交，另一笔报 `1213`（SQLSTATE `40001`）。死锁图显示两笔事务都持有 `idx_iam_member_export_tenant_status` 末端区间的锁，并等待在同一区间插入。 |
| 范围清理与工作线程修改同一到期任务 | 固定两种操作的交错顺序后复现 `1213`。清理持有二级索引锁并等待主键；工作线程持有主键并等待二级索引。此复现说明后台状态更新也能参与死锁。上一轮 HTTP 没有保留当时的死锁图，不能仅凭应用日志断定属于这两种顺序中的哪一种。 |
| 仅并发插入两条新任务 | 两笔都提交。 |
| 按主键清理到期任务，同时登记新任务 | `EXPLAIN` 使用 `PRIMARY`。20 轮均提交；到期任务标为 `EXPIRED` 并清空快照，未到期任务及另一租户保持原值。这是候选 SQL 验证，应用尚未修复。 |

复现空表场景时，开两个连接分别 `START TRANSACTION`，各执行同一条 `UPDATE iam_member_export SET status='EXPIRED', member_ids=NULL, failure_reason=NULL WHERE tenant_id=? AND expires_at<=? AND status IN ('PENDING','RUNNING','SUCCEEDED')`。两笔清理都结束后，各插入一个不同主键、同一租户、未来过期的 `PENDING` 任务。提交幸存事务，再从第三个连接运行 `SHOW ENGINE INNODB STATUS` 获取死锁图。

## 修复建议与验收门槛

2026-11-10 用户确认实施成员 JSON 导出与成员工作簿导入的按主键清理方案。继续在原 active change 内完成，部门工作簿先独立复验。两个成员链路使用非锁定查询按 ID 读取候选，每次只更新一条主键记录。任务登记、版本检查、同事务审计和提交后派发继续由原入口负责。沿用原数据库结构及 API。

优先把两条已复现链路的到期清理由范围写入改成普通读取候选 ID，再按主键有序更新。更新时仍校验租户、截止时间和可过期状态；候选为空时不发 `UPDATE`。保留现行 24 小时期限、过期清除快照或工作簿产物、任务和审计原子登记、提交后执行，以及各自现有的版本、身份和取件规则。部门工作簿还需单独验证，并校准对象删除与数据库提交的顺序。

## 部门工作簿修复设计

用户要求继续完成剩余工作。本修复沿用 active change 的导入契约。候选查询只读任务 ID，按主键升序逐行更新，更新条件复核租户、截止时间和任务状态。登记事务提交后才删除到期产物。删除失败时，已过期记录保留对象路径供下次读写重试，取件仍返回 404。新上传的原文件在登记回滚时补偿删除。期限、权限、任务与创建审计的原子性、导入逐行语义和 API 保持现行约定。

验收覆盖双节点有无到期任务的并发登记、与后台状态更新竞争、实际对象删除、删除失败重试、登记回滚保护旧对象及补偿删除新对象，以及跨租户和非发起人取件拒绝。沿用现行字段，无需数据库迁移。应用回退可沿用现有表，待删对象宜在修复版本上清理后再回退。

新制品双节点四轮各并发 8 笔，32 笔全部登记、执行并从另一节点读回，每笔有一条创建审计。复跑后台状态更新竞争时，两笔操作都成功，锁等待只涉及主键。三轮到期清理共核对 48 个 MinIO 对象，删除前均可读取，删除后均返回 404。确认 24 小时期限、无权限导入 403、非发起人及跨租户取件 404。

实际注入审计失败后，旧任务状态和 MinIO 产物随回滚保留，新上传的对象被补偿删除。随后读取状态触发到期清理，旧对象实际删除。服务回归额外注入对象删除失败，确认到期取件仍拒绝、路径保留，后续请求删除成功后清空路径。

## 2026-11-11 平台成员续验发现

### 允许字段未显示在列表

独立浏览器会话中，普通角色的成员 context 返回 phone=MASKED，但列表只显示登录账号、状态、名称和操作。字段设置允许手机号；权限变化后指定目标的 email 变为 FULL、另一目标保持 HIDDEN，详情和接口投影均正确，列表仍缺少允许的联系列。不存在后端原值泄露。

源码显示，成员页先以未取得 context 的列初始化通用列设置；`useTableColumnSetting.hydrate/emitSelection` 会将当时的选择写入用户偏好。异步加入的可见字段再消费已有选择。这是初始化偏好与动态列交互的排查方向，尚未修改实现。修复须保留用户主动隐藏/排序意图、HIDDEN 门禁及逐对象投影，不能通过强制全选或固定显示字段修补。

退出标准：无已保存偏好时按当前允许列显示；有主动偏好时保留；权限新增/撤回字段后列表与设置一致，隐藏值不进入布局，两个身份和空列表/跨页均复验。

### ACTIVE 列表的同秒精度不一致

用当前秒的 0.2 秒作为 validFrom，在该秒 0.35–0.5 秒之间真实创建分配，确保请求时已经生效。两个节点详情均返回 ACTIVE，但两个节点同一秒的成员 ACTIVE 分配列表均不包含新记录；下一整秒两边均包含。此前成员角色差量保存时出现 23→24 的短暂读回延迟由该问题解释，数据库角色变更没有丢失。

`AssignmentRepository` 的 STARTED/FUTURE/EXPIRED/UNEXPIRED 过滤使用无精度 `CURRENT_TIMESTAMP`，MySQL 只比较整秒；授权求值及详情状态保留微秒精度，产生不一致。修复须覆盖生效和到期两端，保留状态定义、权限、排序及数据库分页；不能用前端重试或放宽有效期掩盖。

退出标准：固定微秒时间同时核对两节点详情、ACTIVE/PENDING/EXPIRED 筛选及 total，创建或到期同秒无漏项/错分。详见[脱敏运行结果](./PLATFORM-MEMBER-RUNTIME.json)。


### 2026-11-11 列设置与状态筛选修复复验

列设置实际存储键为 `in-column-setting:<用户键>:<tableId>`，值包含 selected/order；沿用旧键和旧数组兼容。主动隐藏可解释某个用户的缺列，不能仅凭接口允许就认定缺陷。初始化自动保存不完整列、排序未补入新增列是两个实现问题：前者污染默认偏好，后者会让重新勾选不生效。本轮仅用户切换/排序时写入，初始化只读；新增允许列补入顺序，已有 order 内未选中的列继续隐藏。暂不可见字段仍保留本地偏好，但不发送到当前表格。未清空、迁移或重置用户浏览器 localStorage。

双节点独立 Chrome 会话验证干净默认、保存隐藏/排序后刷新、旧不完整顺序、手动切换和空列表均通过。真实权限变化后邮箱进入/退出布局，目标内 FULL、另一目标 HIDDEN、无逐行请求，原手机号隐藏及存储值保持。用户当前平台页面已回到登录页，其具体偏好未直接核验；不把全部缺列都归因于代码。

分配四种时间条件、委派来源/候选、有效角色摘要和未到期版本分布使用 CURRENT_TIMESTAMP(6)。保持原状态优先级、数据库分页、排序、权限及半开区间。一次性真实 MySQL 的固定时钟验证开始/截止前后 1 微秒及相等边界、候选 count/page 和来源投影。最终制品双节点同秒 HTTP 的 ACTIVE/PENDING/EXPIRED、total 和详情一致；跨过边界后正确变更。新分配的有效角色摘要在同秒返回，角色差量保存另一节点首读 24 条。

继续补验 MR04：真实预览成功后另一节点抢先更新成员，旧 PATCH 和再次预览均 409，保留本页草稿，24 条分配及其版本/范围保持，另一节点的成员修改保留。修复退出条件已满足；S04/S05 其余边界及人工门禁继续开放。详见 [本轮脱敏证据](./COLUMN-STATUS-RUNTIME.json)。

2. SN07 首次锁定 500：既有锁定行更新路径正常，首次写入因适配器未填 createdAt/updatedAt，MySQL 非空约束先于最后超管检查失败。框架适配器用单次 UTC 时钟补齐创建/更新时间，锁定时间复用；现有行保留 createdAt。没有提前提交初始化行、改权限/事务或放宽最后超管保护。新增 2 项回归通过；最终制品 7 类最后超管破坏操作和 5 类不可用备份均 400 ObjectInUse、失败快照无残留。双节点并发一成一拒且始终保留可用超管，SYSTEM 候选/授予/只读边界同时通过。
3. 首次窄屏抽屉：720px 固定 size 在 390px 首开时 x=-330，菜单页签位于视口左侧。公共容器仅增加 max-width:100%，390px 实际 x=0、宽 390；桌面仍宽 720，真实菜单页签与树可操作，23 项相关回归通过。

## 2026-11-11 独立对象服务错误分析与修复

- 动态 Feign：未标 @FeignClient 的白名单 RPC 被 Sentinel 构建器当作声明式客户端读取 fallback，IAM 启动 NPE。无注解分支保留 Sentinel 默认处理，不禁用熔断；3 项回归及最终远程调用通过。
- 示例装配：后续 IAM API 已自动启用 Feign，样板重复声明导致 Bean 冲突；沿标准数据库/Redis/安全装配后 Boot Jar 可独立启动。字段清单类 final 阻止 @Permit 代理，移除 final 保留全部权限和签名。
- 对象在线身份：普通 INNER 链只验证内部头，不能恢复对象 RPC 需要比较的在线成员。增加仅匹配该 POST 的真实 Bearer/在线会话链；来源过滤置于异常转换之后，缺来源 403，纯清单仍无用户启动依赖。坏签名、仅内部头、身份/租户替换均拒绝。
- 跨服务失效：SDK 在事件总线之前评估订阅条件，漏注册而继续读热授权。按统一分层缓存排序到总线之后；实际双 SDK 撤权首读 403、重授恢复、自然到期和组变化通过，无 LKG/地板放行。
- 配置与协议：IAM 超时应按既有 contextId iamAuthorizationService 配置；零字段默认 Map 被配置绑定器省略时仅规范化为合法空，有字段仍严格缺省拒绝。v2 内部错误按已发布 400/403/503 映射，旧内部接口不扩大；SDK 保留项目 InFeignException 已知原因，未知故障归不可用。

已排除的探针/环境问题：列表原生数组误按 R 解析；AssignmentRecord 的分配位于 assignment 内；平台分配使用 revision_id 而非租户 role_id；默认成员分页含暂停；1200ms 按钮节流不能用 1100ms 点击探针；组扩大当前先被 PolicyConflict 拒绝。统计重启参数曾丢失带空格日志格式，旧 0-RPC 数字无效，已用完整路径和正计数重测。运行 Jar 曾被构建覆盖造成类加载错误，重复发现地址也曾造成测试连接故障；均改为唯一地址与冻结制品后重跑，不计产品失败。初始 SQL 夹具的中文编码也已修正并重拍页面。
