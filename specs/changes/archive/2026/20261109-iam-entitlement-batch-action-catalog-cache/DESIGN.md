# 设计

## 开通与人群批量查询

在 `IamTenantAppEntitlementMapper` 增加按候选应用 ID 集合分组的查询，复用现有 `IamMembershipSql` 的部门可达与成员组 CTE，以及单应用查询的人群和期限谓词。SQL 按可信 `tenantId`、`memberId` 和候选应用限定，同一条语句计算各应用的命中和截止。Repository 将稀疏结果索引为应用 ID 到命中和截止的映射。输入去重，空输入直接返回空结果，缺失应用按未命中处理。

- `SessionRepository.accessibleApplications` 仍以启用应用列表及既有排序为候选，一次批量校验后按原顺序过滤。保留平台与租户拥有者分支。
- `TenantAuthorizationEvaluator` 从本次有效角色定义所引用且已启用的操作收集去重应用 ID，一次读取开通与人群。原求值循环继续检查委派、范围、参数绑定和截止时间，按应用 ID 读取本请求内的匹配结果。拥有者分支和当前角色头、成员身份、委派等事实读取保持原契约。
- 两个入口共享批量 SQL 的规则。一次 `bootstrap` 可以包含权限求值和应用列表装配各一次校验，以保留两个入口独立使用及原数据流。结果仅用于当前调用。

## 操作目录单层 Redis

调用点为平台 `ActionCatalogService.getActionCatalog` 和租户 `EntitlementService.tenantActionCatalog`。先执行入口现有鉴权、租户开通及应用存在性检查。使用当前应用行生成目录头。缓存载荷为现有 `ActionCatalogResource` 和 `ActionCatalogItem` 组成的固定 JSON 列表，平台完整视图和租户启用视图分别存储。配置层装配该 JSON 解码器，基础设施层只负责 Redis 读写。授权、开通和应用存在性失败直接走原错误处理。合法空目录可以缓存，加载失败和错误响应直接返回原错误。

使用 IAM 自有的 `StringRedisTemplate` 读写，键由部署命名空间、缓存格式版本、应用 ID、共享代次及可信入口视图组成。共享代次按应用隔离。代次键缺失时以带过期的原子写入竞争生成随机令牌，始终使用胜出的令牌。数据键过期上限为 **60 秒**，按该次装载开始时计时，读取命中时不续期。代次键建议 120 秒自动回收，代次轮换后旧数据等待 TTL 回收。

对应用、资源、操作的相关写入，在其数据库事务中登记应用级目录变更，提交后使共享代次失效。覆盖应用新增、更新、启停、删除、整包创建、`purge`，资源新增、更新、删除，以及操作新增、更新、启停和删除。回滚时保留原代次。并发加载沿用发起读取时取得的代次，失效后发起的读请求使用新代次。事务内读取绕过 Redis，防止未提交数据进入共享缓存。已有授权失效事件继续服务原消费者。

Redis 配置可用时自动读取和回填。缺少 Redis、缓存读失败、载荷损坏或连接不可用时走数据库。缓存写失败仍返回已读取的数据库结果。提交后失效失败计数并记录日志，已有目录展示数据按原 TTL 过期。使用低基数指标记录各视图的命中、未命中、回源、写入失败和失效失败。数据库加载异常保持原语义。

## 发布与回滚

首期使用现有表结构和接口，随服务版本启用目录缓存。回滚时切回原版本，目录缓存键由 TTL 回收。`ingot.iam.action-catalog-cache.redis-key-prefix` 默认 `in:iam:action-catalog`，不同 IAM 库共用同一 Redis 数据库时分别配置。数据库脚本直接更新目录时使用新命名空间或定向失效。

## 测试策略

- 基于 `TenantLiveMySqlHttpTest` 的两个 HTTP 节点验证真实 Mapper 和即时授权，在相同数据下对比 1 与 16 个应用的 SELECT 数。重点覆盖指定成员、直接与继承组、部门下级、期限边界和跨租户。
- 使用隔离 MySQL 与 Redis 验证目录冷读、热读、查库回源、载荷损坏、断连恢复、并发和提交回滚，并对比平台、租户两类响应。使用 SQL 计数或 Mapper 执行记录单独验证目录命中跳过资源和操作装载。
- 按 [基线](./BASELINE.md) 的身份和场景复测，记录延迟、SELECT 和缓存命中率。优先用 SQL 次数验证结构性收益，用重复测量验证端到端收益。
