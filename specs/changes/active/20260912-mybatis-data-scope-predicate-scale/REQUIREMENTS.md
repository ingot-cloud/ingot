# Requirements

## 用户场景

1. 中小租户（单租户部门大约几十到几百、索引齐全）继续使用已上线的 `{scopeColumn} IN (:deptIds)` 与本人 `OR` 部门，查询计划与结果与父 change 一致，不因本能力上线而变慢或语义偏移。
2. 组织树增大到展开后的部门 ID 达到上千、上万，或 `IN` 无法稳定走 `(tenant_id, 部门列)` 索引时，`DEPT_AND_CHILD` 改为按授权根部门查子孙（闭包表或物化路径），禁止把整棵行政树打进一条 `IN`。
3. 「本人 OR 部门」成为热路径且 MySQL 放弃索引、出现全表扫描时，拆成可分别走索引的 `UNION ALL`（本人一条、部门一条），禁止为迁就 `OR` 做全表扫描。
4. 租户管理员 / 超管对该资源范围是 ALL 时，仍然不加行条件，不要为「看起来像很大」生成巨大 `IN` 或闭包查询。

## 业务规则

- 行过滤必须下推 SQL。数据量变大只换谓词形态，不得改回应用内存过滤。
- 授权计算结果不变：ALL / SELF / DEPT / DEPT_AND_CHILD / CUSTOM 的可见行集合与父 change 语义一致；本 change 只改变谓词形态和部门子孙的求值位置。
- `CUSTOM` 仍是调用方指定的部门 ID 集合，继续 `IN`，不走闭包展开。
- `DEPT`（仅当前/绑定部门，不含子孙）ID 数量通常很小，继续 `IN`。
- 无规则、空部门、跨资源套用当前帧仍为 `1 = 2`。
- 分页、count、UPDATE、DELETE 与 SELECT 使用同一范围语义；若采用 `UNION ALL`，必须保证这四类语句结果与单条 `OR` 谓词等价（含去重与分页正确性）。
- 升级路径按租户或按请求规模启用，不是全库默认改写。未达触发条件时行为与父 change 默认谓词完全一致。

## 边界与非目标

- 不修改资源、权限、角色 data-rules、功能鉴权注解的产品模型。
- 不为「部门不多但表很大」单独发明第二种范围语义；大表仍靠既有 `(tenant_id, 部门列)` / `(tenant_id, 归属用户列)` 索引。
- 不在本 change 引入字段级脱敏、显式拒绝规则、复杂布尔权限表达式。
- 不把 PMS 用户 / 部门 / 角色管理表批量纳入行过滤。
- 物化路径与闭包表二选一作为 `DEPT_AND_CHILD` 的规模实现，不得同时维护两套互相不一致的子孙求值。

## 验收标准

- [ ] 未达触发条件的租户：生成的 SQL 仍为默认 `IN` / `OR` / 等值 / `1=2` / ALL 不加条件，与父 change 单测口径一致。
- [ ] 达触发条件的 `DEPT_AND_CHILD`：SQL 不再包含上千级部门 ID 的 `IN` 列表；子孙求值走闭包（或已选的物化路径）；结果集与展开 `IN` 的对照查询一致。
- [ ] ALL 范围永不生成部门 `IN` 或闭包子查询。
- [ ] 「本人 OR 部门」在启用 `UNION ALL` 策略后，EXPLAIN 不再因该 `OR` 出现全表扫描；分页与 count 行数与启用前语义一致。
- [ ] 部门树增删改后，闭包 / 路径与邻接表 `pid` 一致；软删部门不出现在子孙结果中。
- [ ] 任何规模下都不在应用层过滤已查出的业务行。
