# 调度运行与验收

## 配置

未配置时使用下列默认值，原 `worker-enabled` 键保留：

```yaml
ingot:
  iam:
    role-applications:
      worker-enabled: true
      fallback-scan-interval: 60s
      active-batch-delay: 250ms
      queue-capacity: 256
```

配置在启动时校验，改变后重启对应IAM节点。扫描间隔至少10秒，批次间隔正值且小于10秒，队列容量为正数。数据库租约固定30秒，不由节点本地时钟决定。队列容量同时用于本地提示及异步发送队列，只有提示会因容量不足被丢弃；数据库记录始终保留。

## 多节点工作方式

每个开启worker的IAM节点都接收提示和执行扫描，无主节点选举。正常确认事务提交后本地立即排队，其他节点收到广播后等待200～1000毫秒再检查任务主键。后续批次按ID安排，单节点只并行一个批次；同一角色及不同节点之间仍由原数据库锁、租约和唯一RUNNING约束保障。

空闲扫描完成后默认60秒再次扫描；启动首次扫描随机分散在0～60秒。每次SQL只选任务ID、角色ID，使用100条游标页；发现很多任务时一轮可有多个分页SQL，但没有任务时每节点约一分钟一次领取查询。HTTP查询任务进度以及按ID续批的SQL不属于集合发现扫描。

框架事件总线过滤自身消息，因此本地唤醒和广播分别执行。事件为`iam.role-application.wakeup`，由框架通道前缀生成实际通道；不修改已有授权失效事件。Redis故障或`ingot.event-bus.type=none`时，本地确认仍可立即执行，遗漏/异节点任务通过扫描恢复。网络发送及订阅在独立线程中，不阻塞执行器或扫描器。

关闭某节点worker后，该节点不接收或领取任务，HTTP确认仍可向其他节点广播。全部worker关闭时任务保留RUNNING并等待后续恢复，不会在HTTP线程执行。发布版本但未确认应用不会发送唤醒。

## 故障与停止

- 数据库异常扫描按60、120、240、300秒退避，成功查询后回到配置扫描间隔；空扫描无业务INFO。
- 通知重复、队列溢出或网络失败不会删除持久任务；队列满后保留扫描游标，下一轮继续，扫描到末尾后回到起点。
- 已提交批次保留；业务冲突、撤权或依赖故障仍按原规则暂停。确认继续需显式重新预检，通知不会自动恢复PAUSED。
- 关闭时取消新调度并等待当前批次最多30秒，不强制中断正在提交的事务；正常取消订阅，异常退出由其他节点在租约过期后接续。
- 数据库健康、执行队列无积压时，默认接续发现窗口约30秒租约＋60秒扫描＝90秒。积压、数据库故障及自定义更长扫描间隔会延长窗口。

## 指标

使用已有Actuator/Micrometer注册表，无额外监控轮询：

| 指标 | 含义 |
|---|---|
| iam.role.application.discovery | 领取发现的SQL页查询次数 |
| iam.role.application.discovery.errors | 发现流程失败次数 |
| iam.role.application.lease.conflicts | 事务内领取竞争失败次数 |
| iam.role.application.batch.duration | 按ID执行尝试耗时 |
| iam.role.application.batch.errors | 无法完成执行或持久暂停的异常次数 |
| iam.role.application.queue.depth | 本节点未结束提示数量，包含当前执行项 |
| iam.role.application.hints.dropped | 队列溢出等导致提示丢弃次数 |

大范围任务中队列深度高于零或提示丢弃不代表持久任务丢失；结合原任务明细和状态判断。长期领取冲突/故障需检查数据库、Redis和节点配置，既有任务暂停原因继续保留在数据库。

## 发布与验收

本次只更新后端，无新SQL或前端发布。可以逐节点滚动升级；直到全部旧IAM节点退出前，日志仍可能存在旧的一秒扫描。回退代码使用同一任务表及租约，不删除任务、进度或审计。正常回退前可按原运行手册在所有节点关闭worker，等待当前批次结束。

jy实际环境验收：至少两个开启worker的IAM节点空闲观察10分钟；核对每节点约一分钟扫描一次、本节点确认后无积压时1秒内开始领取。关闭广播验证遗漏提示能恢复，再终止执行节点验证租约接管及完整审计。隔离自动化已验证相关边界，但不替代真实配置/连接池/节点运行验收。
