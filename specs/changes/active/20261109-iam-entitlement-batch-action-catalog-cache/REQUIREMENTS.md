# 需求与验收标准

## 用户场景

- 普通租户成员登录后读取 `GET /v1/me/bootstrap`，或刷新 `GET /v1/me/capabilities` 时，应用数量增加不会导致逐应用查询开通和人群。
- 平台管理员或有权的租户成员打开应用操作目录时，重复读取同一应用的资源和操作能复用 Redis 中的目录。
- 管理员调整角色、分配、委派、应用开通、人群或操作状态后，随后发起的租户授权请求按当时的数据库事实求值。

## 业务规则

- 批量查询沿用已校验的租户和成员身份。应用开通的开始包含、截止排除，沿用 UTC 数据库会话。保留全组织、指定成员、组继承、部门直属与下级包含规则，以及不限期开通的截止语义。
- 拥有者继续实时获取已开通应用及其权限，适用现有的人群例外。普通成员仍需满足当前人群和开通条件。空结果按无匹配处理，数据库失败沿用现有错误与拒绝语义。
- `GET /v1/platform/applications/{id}/action-catalog` 和 `GET /v1/tenant/applications/{id}/action-catalog` 每次执行现有准入和应用检查。租户入口继续检查该租户的有效开通。平台视图包含停用条目，租户视图按现有规则返回启用目录并剔除没有操作的资源。
- Redis 只存储目录展示数据。数据库仍是应用存在性、开通、成员、角色、委派、操作启停、授权范围和到期判定的来源。
- 保持现有 HTTP/RPC 契约、排序、错误码与身份隔离。范围限于开通与人群批量查询，以及两个 `action-catalog` 入口的单层 Redis 缓存。

## 验收标准

- [x] A1 普通成员从 1 个应用扩至 16 个应用，每次授权求值至多执行 1 条开通与人群查询。普通成员应用列表装配至多额外执行 1 条同类查询。空候选跳过该查询。
- [x] A2 覆盖命中、无开通、停用、未来生效、到期、无期限、不同人群和跨租户，验证接口结果、权限集合和有效期语义。双节点验证角色保存或停用、委派撤销、开通与人群变更等在提交后的下一次租户授权请求生效。
- [x] A3 配置 Redis 后两类目录自动使用缓存，冷读、热读和查库回源的响应一致。热命中省去 2 条资源、操作装载查询，应用存在性及租户开通仍实时检查。拒绝请求不能通过热缓存取得目录。
- [x] A4 双节点覆盖提交、回滚、目录写入覆盖、并发旧回填、缓存损坏、Redis 断连与恢复。失效失败时展示数据有 TTL 上限，授权仍按数据库事实判断。
- [x] A5 用 [基线夹具](./BASELINE.md) 复测 SQL 数、P95 和 P99。16 应用下 `bootstrap` 与 `capabilities` 的 SELECT 数分别较基线减少至少 30 和 15。直接查库、冷读和热读的数据及收益已在本地验证。
