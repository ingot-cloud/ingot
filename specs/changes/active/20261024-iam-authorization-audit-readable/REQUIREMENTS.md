# Requirements

## 用户场景

- 组织管理员在“安全与合规 › 授权审计”中按时间倒序浏览当前组织的授权变更，可以连续翻页，翻页期间有新审计写入时，不出现重复或遗漏。
- 管理员按操作者、对象类型、变更类型或时间段筛选。数据量达到百万级时，响应时间不会随翻页深度或总量明显上升。
- 管理员看到的操作者、目标和变更内容都是名称与可读描述（例如“名称：研发部 → 研发中心；状态：启用 → 停用”），不需要拿 ID 去别处反查。
- 平台管理员在平台授权审计中获得相同体验。

## 业务规则

1. **分页**
   - 按 `occurred_at DESC, id DESC` 稳定排序，使用不透明游标翻页，每页 1–100 条，默认 20 条。
   - 不返回总数。用 `hasMore` 判断是否还有下一页。
   - 游标只编码排序键，不携带域、租户或筛选条件。域和租户始终从可信身份恢复，伪造的游标不能越界。
   - 游标格式非法时返回 400 `InvalidArgument`。
2. **筛选**：沿用 `actorMemberId`、`targetType`、`targetId`、`changeType`、`from`（包含）、`until`（不包含）。筛选在 SQL 中与游标条件同时生效。
3. **对象名称解析**
   - 每页一次性批量解析本页涉及的对象：操作者、目标、关联角色分配、来源委派，以及变更值中的角色、角色版本、成员、部门、用户组和接收对象。
   - 每个对象的结果为以下三种状态之一：
     - 可见 `VISIBLE`：查看人持有该类对象的读取权限，且对象在其数据范围内。成员名称还要再按管理场景的字段策略投影。
     - 无权查看 `HIDDEN`：不满足可见条件。此时不返回名称，也不返回存在性之外的任何信息。
     - 已删除 `DELETED`：对象已不存在。如果本条审计的 `before.NAME` 留有名称，就用它作为名称。这个值本来就已经在审计差异里返回，不构成新的泄露。
   - 解析失败（例如数据库异常）时整页返回 500，不降级为展示 ID。
4. **兼容旧数据**
   - 历史批量任务审计的 NAME 是类型编码，平台委派审计的接收对象是 `created`、`before`、`after` 占位文本。读取时原样返回，由前端识别后展示为“接收对象已调整（未记录明细）”等说明，不回填数据。
   - 修复后，新写入的批量任务不再写 NAME，平台委派的接收对象写真实的 SubjectRef 列表。
5. **安全**：不新增跨域或跨租户读取；不返回凭证或联系方式；名称解析遵守现有的成员可见范围和字段策略。

## 边界与非目标

- 不支持跳转到第 N 页，也不显示总条数。
- 不支持按名称模糊搜索操作者或目标。前端改为通过选择器传入 ID，接口仍然按 ID 精确匹配。
- 改名后的对象显示当前名称，变更前后的名称以差异字段为准。
- 不调整审计保留期、分区或冷数据归档。如有需要另立变更。

## 验收标准

- [ ] 两个域的接口按游标翻页，`hasMore` 和 `nextCursor` 正确；多条审计 `occurred_at` 相同时，跨页不重复、不遗漏。
- [ ] 翻页过程中新写入审计，不影响已拿到的游标的后续结果。
- [ ] 非法游标返回 400；拿 A 租户的游标去请求 B 租户，只返回 B 租户的数据。
- [ ] 筛选与游标组合正确，时间区间保持半开。
- [ ] `references` 能覆盖本页出现的所有对象引用，并正确区分可见、无权查看、已删除三种状态；成员名称遵守字段策略。
- [ ] 每页 SQL 次数有固定上限：一次审计查询，加上每种引用类型至多一次批量查询，与条数无关。
- [ ] MySQL `EXPLAIN` 显示租户时间、操作者和目标三类查询分别命中对应索引，不出现 filesort 和全分区扫描。
- [ ] 新写入的批量任务审计和平台委派审计不再出现编码或占位文本。
