## 1. 交付边界与环境

目标是让前后端在可重建的独立环境中验证本 change 已实现的所有能力，不只使用平台治理账号浏览列表。正式初始化继续由现有 DDL、`006_bootstrap.sql` 与 `PlatformBootstrapService` 负责；测试夹具不加入正式种子，不恢复历史迁移方案。

后续工具落在 `tools/iam/test-data/`，交付 README、场景清单、构建/检查/重建入口及 Bruno 场景请求。使用 Python 标准库编排既有接口；不增加生产测试控制器、不扩展生产权限或认证绕过。读取配置指定的 Gateway、Auth/BFF、数据库、Redis 命名空间和两域四站地址，服务启动与部署仍使用既有配置。配置缺失时明确失败，不猜测现有开发库。

- 初始化顺序以 `databases/iam/README.md` 的权威 DDL 清单为准：IAM DDL、导出任务表、框架安全 DDL、正式目录种子、受控平台账号。复用现有发号能力，测试对象不占用正式种子的保留 ID。
- 环境必须有独立数据库及 Redis 命名空间；多实例用例共用该测试库/Redis。配置携带测试环境标识，工具记录并检查环境清单，拒绝向未登记目标执行重建。
- 账号通过框架初始化/正式账号 API 创建；后续组织、角色、授权、策略等通过真实管理接口生成，保留真实审计和失效行为。凭证通过环境变量或本地未入库配置提供；运行报告只记录账号用途，不打印密码、token、Cookie 或隐藏字段原值。
- `seed-manual-verification.sql` 继续作为历史小型人工夹具保留。本方案不依赖其中两个固定账号，不额外复制一套治理目录；原 Bruno 案例可复用步骤，但须以本次生成的 ID/版本重新绑定。
- 正常数据准备可通过正式 Auth 认证入口完成；BFF 四站登录另用浏览器执行，接口准备成功不等于 BFF 验收成功。

## 2. 构建、重复执行与重建

工具提供 `prepare`、`verify`、`reset` 三类显式命令，参数和帮助随测试数据 D01 实现。`prepare` 写入场景版本、runId、UTC 基准时间 t0、环境指纹和自然键→真实 ID/版本映射到本地运行清单（不提交 Git）。同一 runId 重跑复用既有对象，不覆盖测试人员修改；遇到配置漂移报告差异并要求重建场景，不静默改回。

角色版本、成员和所有者变更等不可随意恢复的场景使用独立场景租户/对象。`reset` 只重建已登记的独立测试环境，必须显式指定环境标识和重建参数；不能自动清理任意开发库。重新运行得到新的 ID 时，Bruno 环境和验证报告使用新映射，不依赖硬编码数字。

`verify` 分为数据一致性检查和业务行为检查。前者核对对象数量、引用、域、版本和期限；后者以真实测试身份请求接口，记录预期/实际。数据库直接写入仅限权威初始化；确需构造运行时无法直接产生的故障，以隔离测试注入或明确运维步骤执行，不能伪造生产审计、导出成功行或历史测试结果。

未来/过期期限按 t0 计算，临近到期用例执行前重新建立短期授权并记录服务端时间；不使用随日历失效的固定日期。并发、撤权、停用、组变更、导出失败等操作在独立场景步骤中触发，执行后可重建，不能靠静态行证明。

每个场景执行后的报告必须包含：场景版本/runId、环境与代码版本、账号类别、实际入口、对象自然键/ID、步骤、预期与实际允许/拒绝和可见范围、结果、脱敏证据、恢复/重建方式。表中“预期”均是后续验收目标，不是当前通过结论。

## 3. 身份与基础数据

账号使用 `iam-test-<用途>` 前缀，自然键纳入清单。至少提供下列可登录身份；停用/移出用例使用专用账号，避免污染常规联调身份。凭证只从测试环境配置读取。

| 身份键 | 成员关系与用途 |
|---|---|
| platform-governor | 仅平台治理成员；治理目录、账号、租户及共享角色管理 |
| platform-reader | 仅平台只读角色；无写按钮及手工写请求拒绝 |
| owner-a / owner-b | 租户 A/B 所有者；治理权限与业务授权区分 |
| dual | 同一账号有平台和 A/B 成员；双域并行、单/多租户选择及隔离 |
| reader-a | 研发只读，手机号脱敏；无编辑/移出/导出 |
| editor-a | 编辑研发，同时另有全组织查看；验证操作与范围不跨角色拼接 |
| grantor-a | 受限分配管理员；固定版本、接收人、范围和期限上限 |
| ordinary-a | 普通通讯录权限，无后台成员管理权 |
| multi-dept-a / no-dept-a | 多部门与无部门身份，测试对象能力差异 |
| no-access / suspended / disabled | 无业务授权、局部成员暂停、全局账号禁用；分别建立独立对象 |
| owner-transfer-src / owner-transfer-dst | 仅用于 TD15 的专用组织所有者与接收人，不复用 owner-a |
| export-batch | 租户 A 内至少 250 条普通成员的批量账号前缀，不用于日常登录联调 |

至少两个租户：A 包含根部门、研发及其下级、销售、空部门；B 使用相似名称但不同 ID 验证隔离。A 生成至少 250 条普通成员作为分页与导出数据，另建多部门与无部门边界样例；平台组候选及应用选择器分页也需大于单页的数据集，由对应场景单独生成。

角色包含固定共享 v1/v2、独立租户自定义和基于 v1 的差异角色；不把全部能力塞入一个超管角色。业务目录测试应用用于验证开通/人群/角色/菜单和诊断；真实读写范围测试使用已有成员、部门等执行器，不把“新增资源登记”当作已开发新业务接口。

## 4. 可执行场景卡

前端复用同一 TD 编号，并在 P26 证据中记录 runId。数据准备与动态验证分开：静态行只能证明对象存在，不能代替撤权、并发、到期、多实例和四站登录。

重建列中的 `prepare`/`reset` 均作用于已登记测试环境；未标明独立对象的场景可在同一 runId 上重复 verify。

## 6. 无法只靠数据覆盖的执行条件

下列用例必须单独准备运行条件；缺条件时记录阻塞和局部替代范围，不得用静态数据或 Mock 报全链路通过。

| 条件 ID | 覆盖场景 | 执行条件 | 数据能证明什么 | 不能替代什么 |
|---|---|---|---|---|
| XC01 | TD12、TD14 | 至少两个 IAM 实例共享测试库与 Redis/任务存储 | 任务行或授权行存在 | 跨实例下载、缓存广播、故障 503 |
| XC02 | TD12 | 可注入或运维触发的 Redis/远端不可用 | expiresAt 字段 | 热窗口截断与 503 语义 |
| XC03 | TD06、TD15 | 双客户端并发（两 token 或两浏览器） | 当前 version | 409/零部分更新 |
| XC04 | TD16 | 真实或测试 OSS、社交供应商、Security/Auth/Member RPC | 配置项存在 | 上传/社交/锁定计数真链 |
| XC05 | TD11 | 平台字段上限：有管理入口则走接口，否则测试层注入，不新增生产配置 API | 租户规则 | 平台上限引擎 vs UI 可配置范围需分报 |
| XC06 | TD17 | 四不同 host；生产形态 HTTPS 与 Secure Cookie | 账号能 Auth 登录 | host-only Cookie、CSRF、ticket 一次性 |
| XC07 | TD17 | Member 登录回归环境 | IAM dual 身份 | Member 原协议未被改写 |
| XC08 | TD14 | 导出失败注入或权限在 RUNNING 中撤销 | 250 成员 | FAILED/EXPIRED/撤权后下载拒绝 |
| XC09 | TD18 | 查询计划/慢查询观察手段 | 大数据量行 | 无 N+1、无内存分页 |

安全、辅助配置和外部存储依赖写入环境清单；配置缺失时工具失败，不默认连开发库。
